## Задача 4. Разведка HTTP через curl

Сервер запущен на порту 9000, потому что 8000 на машине занят другим процессом.

### Три вида строк в выводе curl

`*` - сообщения самого `curl` о том, что он делает: разрешение имени в адрес,
выбор между IPv6 и IPv4, установление TCP-соединения, шаги TLS-рукопожатия,
сведения о сертификате, закрытие соединения.

`>` - байты, которые `curl` отправил серверу: стартовая строка запроса и
заголовки, каждая строка отдельно. Пустая строка `>` обозначает конец
заголовочной части.

`<` - байты, пришедшие от сервера: строка состояния и заголовки ответа. Пустая
строка `<` отделяет их от тела.

Три вида нужны, чтобы разделить три разные вещи: собственные решения клиента,
исходящий поток и входящий поток.

### Разбор стартовой строки запроса

```text
GET /health HTTP/1.1
```

Три части, разделённые пробелами. `GET` - метод, то есть запрашиваемое действие
над ресурсом: получить представление, ничего не меняя. `/health` - целевой путь,
без схемы и имени хоста, потому что имя хоста передаётся отдельным заголовком.
`HTTP/1.1` - версия протокола, в которой клиент готов вести обмен.

### Разбор заголовков запроса

| Заголовок | Кто поставил | Зачем |
|---|---|---|
| `Host: 127.0.0.1:9000` | `curl` автоматически | Обязателен в HTTP/1.1. На одном IP-адресе может обслуживаться много сайтов, и только по этому заголовку сервер понимает, к какому именно обращаются. Путь в стартовой строке имени хоста не содержит. |
| `User-Agent: curl/8.5.0` | `curl` автоматически | Представляет клиента: программу и её версию. Серверы используют его для статистики, а иногда для выдачи разного содержимого разным клиентам. |
| `Accept: */*` | `curl` автоматически | Сообщает, какие типы содержимого клиент готов принять. Звёздочки означают «любой», поэтому сервер волен отдать что угодно. |
| `Content-Type: application/json` | я сам, через `-H` | В запросах POST сообщает серверу, как интерпретировать байты тела. Без него сервер не знает, JSON перед ним или форма. |
| `Content-Length: 44` | `curl` рассчитал по данным из `-d` | Задаёт границу тела в байтах, чтобы сервер знал, сколько дочитывать из сокета. |

Первые три `curl` добавляет сам, даже если о них не просить. Последние два
появляются только в запросах с телом.

### Разбор строки состояния ответа

```text
HTTP/1.1 200 OK
```

Версия протокола, числовой код и поясняющая фраза. Код 200 относится к классу
2xx, то есть к успешному выполнению запроса. Класс задаётся первой цифрой: 1xx
информационные, 2xx успех, 3xx перенаправление, 4xx ошибка клиента, 5xx ошибка
сервера. Фраза `OK` предназначена человеку, программы ориентируются на число.

### Разбор заголовков ответа

| Заголовок | Откуда | Что означает |
|---|---|---|
| `Content-Type: application/json; charset=utf-8` | мой сервер | Тип содержимого и кодировка. Без него клиент не знает, разбирать тело как JSON, как HTML или как изображение. |
| `Content-Length: 65` | мой сервер | Длина тела в байтах. Один из двух способов обозначить границу тела в HTTP/1.1: клиент читает ровно столько байт и на этом останавливается. |
| `Connection: close` | мой сервер | Соединение закрывается сразу после ответа. В HTTP/1.1 соединение по умолчанию постоянное, поэтому без этого заголовка клиент ждал бы в том же соединении следующий ответ. |
| `Server` | example.com | Называет программу, обслуживающую запрос, иногда с номером версии. |
| `Content-Encoding: gzip` | example.com при `--compressed` | Тело сжато, перед разбором его нужно распаковать. `Content-Length` при этом показывает длину уже сжатых байт. |
| `Etag` | example.com | Метка версии ресурса. При повторном запросе клиент присылает её обратно, и если содержимое не изменилось, сервер отвечает 304 без тела. |
| `Cache-Control`, `Age`, `Expires` | example.com | Правила кеширования и возраст копии, которую отдала CDN. `Age` прямо показывает, сколько секунд копия пролежала в кеше посредника. |

### Отличия обмена со своим сервером и с сайтом

1. **Установление защищённого соединения.** У `example.com` в выводе есть шаги
   TLS: `Client hello`, `Server hello`, передача сертификата, проверка цепочки
   доверия по `CAfile`, согласование шифра. У моего сервера ничего этого нет,
   там открытый TCP. Причина в схеме: `https` означает HTTP поверх TLS, `http` -
   HTTP напрямую.

2. **Версия протокола и способ её выбора.** С сайтом `curl` договаривается об
   HTTP/2 через расширение ALPN внутри TLS-рукопожатия: клиент предлагает
   `h2,http/1.1`, сервер выбирает `h2`. С моим сервером договариваться не о чем,
   TLS нет, а значит нет и ALPN; клиент просто пишет `HTTP/1.1` в стартовой
   строке, и сервер отвечает тем же.

3. **Заголовок `Server`.** Сайт его присылает и тем самым раскрывает
   используемое ПО. Мой сервер не отправляет его вовсе, потому что я собираю
   ответ вручную и не добавляю ничего лишнего.

4. **Способ задать границы тела.** Я отправляю `Content-Length`. В ответе по
   HTTP/2 нет ни `Content-Length`, ни `Transfer-Encoding`, потому что границы
   задаёт сама структура кадров протокола: тело заканчивается кадром с флагом
   END_STREAM. При принудительном `--http1.1` эти заголовки появляются снова,
   так как в HTTP/1.1 поток байт сам по себе границ не имеет.

5. **Сжатие тела.** С флагом `--compressed` клиент добавляет `Accept-Encoding`,
   и сайт отвечает сжатым телом с заголовком `Content-Encoding`. Мой сервер
   сжатие не поддерживает и отдаёт тело как есть: для ответа в 65 байт сжатие
   лишено смысла, оно дало бы выигрыш меньше накладных расходов.

6. **Удержание соединения.** Сайт оставляет соединение открытым для следующих
   запросов, что экономит рукопожатия TCP и TLS. Мой сервер закрывает его после
   каждого ответа и честно предупреждает об этом через `Connection: close`,
   потому что обслуживает одно соединение за раз и не может позволить одному
   клиенту удерживать его.

7. **Регистр имён заголовков.** В HTTP/2 имена передаются строчными буквами, это
   требование протокола, и `curl` печатает их так, как получил. В моём ответе по
   HTTP/1.1 они записаны в смешанном регистре, что допустимо: в HTTP/1.1 регистр
   имени заголовка не имеет значения, и мой сервер по той же причине приводит
   имена входящих заголовков к нижнему регистру перед разбором.

8. **Кеширующие заголовки CDN.** От сайта приходят `Cache-Control`, `Etag`,
   `Age`, `Expires`, `Vary` - следы сети доставки содержимого, которая отдаёт
   сохранённую копию вместо обращения к исходному серверу. У моего сервера
   ничего подобного нет: он считает ответ заново на каждый запрос, посредников
   между ним и клиентом нет.

9. **Разрешение имени и выбор адреса.** Для сайта `curl` обращается к DNS и
   печатает найденные адреса IPv6 и IPv4, после чего выбирает, куда идти. Для
   `127.0.0.1` разрешение не нужно вовсе, адрес указан числом, и выбора между
   семействами нет.

### Что раскрывают Server и X-Powered-By

Заголовок `Server` называет программу, обслуживающую запрос, а `X-Powered-By` -
язык или платформу, на которой написано приложение; оба часто включают номер
версии. Для атакующего это готовая разведка, полученная одним безобидным
запросом: зная точную версию, он ищет опубликованные уязвимости именно этой
сборки и применяет готовый эксплойт, вместо того чтобы вслепую перебирать атаки
и светиться в логах. Знание платформы подсказывает и косвенные вещи - формат
сессионных кук, типичные служебные пути, характерные ошибки конфигурации.
Клиенту эти заголовки не нужны: на разбор ответа они не влияют, поведение
клиента от них не меняется. Пользы ноль, польза нападающему ненулевая, поэтому
мой сервер их не отправляет - это сокращение поверхности разведки бесплатной
ценой. Полностью скрыть используемое ПО так не выйдет, остаются другие признаки,
но снимать бесплатную подсказку всё равно стоит.
